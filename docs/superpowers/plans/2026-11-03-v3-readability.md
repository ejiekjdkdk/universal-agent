# V3 可读性审计与整理计划

> 执行方式：使用 executing-plans 在当前会话直接实施；独立审计分别检查风格与行为契约。

**目标：** 在不改变 V3 功能、接口和异常语义的前提下，让新人能够顺序阅读核心执行流程。

**架构：** 保留当前模块边界、SQLite 事务、异步取消和 SDK 资源管理。只整理实际妨碍阅读的代码，不新增通用抽象或依赖。

**技术栈：** Python 3.11、FastAPI、SQLite、官方 MCP SDK、原生 JavaScript。

**规格：** 用户本轮十条代码风格要求，以及 `docs/v3/completion-acceptance.md`、`mcp.md`、`skillops.md`、`triggers.md`。基线为 `2cfa57f`。

## 全局约束

- V3 是当前开发目标和迭代基准；V4、V5 是长期架构愿景，不自动进入本轮实现范围。
- 保留公共签名、协议字段、错误码和错误响应；说明性注释及 Docstring 使用中文。
- 不改变快照摘要、技能签名编码、灰度分桶、数据库结构、事务和权限检查顺序。
- 不移除必要的框架装饰器、SDK 传输类、资源释放、租约围栏和重复授权检查。
- 保留原功能分支。在 `codex/v3-readability-audit` 上修改和提交，沿用私有仓库上传授权；本轮未授权将新修改再次合并 main。

## 审计重点

- 失败的技能评测需要留下审计记录，不能因提前抛错而回滚记录。
- MCP 异常组中的取消必须继续传播，流式响应上限和关闭责任不能丢失。
- 触发器去重、nonce、限流、任务和回执必须处于原事务边界内。
- 灰度选择的身份顺序、JSON 编码和摘要保持不变。
- 中文化说明不得改变从 Docstring 派生的 CLI 帮助和 OpenAPI 契约。
